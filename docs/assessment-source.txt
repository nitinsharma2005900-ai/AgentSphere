1. Project Overview
Build a SaaS platform where organizations configure AI agents, prompts, tools, knowledge sources, workflow steps, 
model providers, usage limits, and human approval. Protect tenant data and external tool access.
2. Business Users and Core Modules
Expected user roles:
 Organization owner
 AI builder
 workflow operator
 auditor
 platform administrator
Core modules to be delivered:
 Tenant management
 agent builder
 prompt versions
 tool registry
 knowledge ingestion
 retrieval
 execution traces
 provider gateway
 usage limits
 human approval
 billing simulation.
3. Learning Outcomes
 Translate a real business problem into a maintainable software architecture and a set of verifiable requirements.
 Build a typed, responsive React/Next.js frontend and secure Node.js/Express REST APIs.
 Design PostgreSQL schemas, constraints, transactions, indexes, and migrations appropriate to the domain.
 Use Python and FastAPI for a clearly bounded processing, analytics, or integration service.
 Integrate external services safely using timeouts, retries, authentication, webhook verification, and idempotency.
 Containerize the system, collaborate through Git/GitHub, and automate quality checks and deployment with GitHub 
Actions.
 Prove correctness through unit, API, integration, end-to-end, security, and failure-path tests.
 Deploy and operate a working application, explain design trade-offs, and respond to production-style incidents.

5. Architecture and Engineering Expectations
Use a modular architecture. The Next.js application is the user interface; Express is the primary business API; FastAPI is 
a separate service for the domain-specific processing/analytics responsibility described in the assessments. PostgreSQL 
is the system of record. Redis may be used for caching and asynchronous jobs.
 Define service boundaries and document which service owns each data entity. Avoid duplicating authoritative 
business data across services.
 Validate all untrusted input on the server. Never rely on frontend-only checks for security or business rules.
 Use database transactions for operations that must succeed or fail together. Document concurrency-control 
decisions.
 Use consistent API response/error formats, pagination, filtering, request IDs, and versioning.
 Keep secrets out of source control. Commit only a safe .env.example with placeholder values.
 Make background jobs retry-safe and idempotent. Record failed jobs and provide a controlled recovery path.
 Include health/readiness endpoints, structured logs, meaningful metrics, and graceful shutdown behavior.
 Document trade-offs. A technically valid alternative is acceptable when the learner explains why it is appropriate.

8. Cross-Cutting Non-Functional Requirements
Security: Enforce authorization server-side; validate input; protect secrets; use HTTPS in deployed environments; apply 
least privilege; avoid exposing sensitive records in logs.
Reliability: Handle timeouts, retries, duplicate events, process restarts, and dependency outages. Do not retry non-
idempotent actions blindly.
Performance: Paginate large collections, index measured query patterns, avoid N+1 access, and provide evidence for 
significant optimization claims.
Accessibility and usability: Use semantic controls, keyboard navigation, visible validation, loading/empty/error states, 
and responsive layouts.
Maintainability: Use clear modules, typed contracts, linting/formatting, meaningful names, migration discipline, and 
documented configuration.
Observability: Use structured logs, correlation/request IDs, health checks, actionable error reporting, and basic metrics.
Data integrity: Use constraints, transactions, explicit state transitions, audit history for important changes, and 
backup/restore validation.
